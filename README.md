# Loco Demo

The Loco implementation of the [OpenTelemetry Demo](https://github.com/open-telemetry/opentelemetry-demo): Astronomy Shop, installed, deployed and observed through [Loco](https://github.com/team-loco/loco).

Astronomy Shop is a microservices application where users browse products, add items to a cart and place orders. This repository installs Loco on a local kind cluster with Flux, deploys 16 of the shop's services with the user CLI, `loco`, and checks the deployment, checkout and telemetry through Loco's public APIs.

## Install Loco

[`gitops/`](gitops/) is an operator repository generated by `locoadm init --single-cluster`. Its combined base selects the release bundle's `./all` entry point; [`clusters/local/values/`](gitops/clusters/local/values/) contains the demo's control-plane and worker overrides. Both roles run on the same kind cluster.

`mise run up` runs the local installation flow:

1. Create kind and the external-service fixtures, then install Flux 2.10.0 with `flux install` against `kind-loco-demo`.
2. Resolve the release bundle pinned by `versions.json` to its digest. Run `locoadm init --single-cluster` into `.state/gitops/` to generate the API environment Secret and OpenBao seal key, then overlay the tracked `gitops/` files while retaining those Secrets.
3. Publish that operator repository to the local OCI registry with `flux push artifact`. Bootstrap an `OCIRepository` and root Flux `Kustomization` against `clusters/local`, then reconcile the bundle's `./control-plane` entry point and its namespace, CRD, infrastructure, config and control-plane layers.
4. Run `locoadm login --api http://api.loco-demo.localhost --web http://console.loco-demo.localhost --device`.
5. Run `locoadm cluster create --name local --region local-1 --kube-context kind-loco-demo`, adding `--tier production` when the selected CLI supports tiers. Core lets the first worker create `local-1`. This writes `loco-agent-join-token` directly into `loco-system`.
6. Publish the repository with the `./all` entry point, reconcile the worker, and wait for `locoadm status` to report enrollment, a healthy heartbeat and no unclaimed admins.

The runner sets `LOCO_TARGET_PLATFORM` in the generated control-plane values to match the kind nodes (`linux/arm64` on Apple Silicon, `linux/amd64` on x86). The tracked values remain portable between hosts.

The control-plane chart creates the shared self-signed ClusterIssuer; the worker references it. `api.systemAdmins` lists `demo@example.test`, so its first sign-in becomes a system admin. The runner approves the device code through the API's `ApproveDeviceLogin` with an ID token from Dex's password grant.

The tracked Secret manifests contain placeholders. The runner supplies the fixture credentials and generates the seal key only in ignored `.state/`; join tokens stay in the cluster. Use encrypted Secrets or another operator-managed secret delivery mechanism for a persistent installation.

The demo supplies these external services as Docker containers next to the kind cluster ([`config/fixtures.yaml`](config/fixtures.yaml)):

| Service | Fixture | Address |
| --- | --- | --- |
| PostgreSQL | `postgres` | `postgres.loco-demo.localhost:5432` |
| OCI registry with `api`, `push` and `pull` identities | `zot` | `registry.loco-demo.localhost:5000` |
| S3-compatible source and backup buckets | `versitygw` | `s3.loco-demo.localhost:19000` |
| OIDC provider with the user `demo@example.test` and a public `loco` client | Dex | `dex.loco-demo.localhost:15556` |

The fixture credentials are in [`config/inputs.yaml`](config/inputs.yaml). The runner uses them for the API environment, registry push/pull Secrets and OpenBao snapshots. The API, dashboard and OTLP ingest listen on `api`, `console` and `ingest.loco-demo.localhost` through the control-plane Gateway.

On the host, every `*.localhost` name resolves to `127.0.0.1`, where kind and Docker publish the API, Dex and storage ports. Inside the cluster, CoreDNS resolves the same names to the fixtures and to [`config/gateway.yaml`](config/gateway.yaml).

## Run locally

Install [mise](https://mise.jdx.dev/) and start Docker. Ports 80, 8080, 15000, 15556, 18888 and 19000 on `127.0.0.1` must be free. Then run:

```sh
git clone https://github.com/team-loco/demo.git
cd demo
mise trust
mise run setup
mise run e2e -- --keep
```

This leaves the demo running. Use `mise run down` when you are finished. To use a local core checkout, replace setup with `mise run setup -- --loco /path/to/core`.

| Task | What it does |
| --- | --- |
| `mise run setup` | Installs the pinned tools, downloads the `loco` and `locoadm` release binaries for the host and checks them against the release's `checksums.txt`, and downloads the upstream chart. `-- --loco` selects another Loco; see [Run unreleased Loco](#run-unreleased-loco). |
| `mise run validate` | Validates `loco.yaml` and the infrastructure-only upstream chart, and builds the GitOps cluster root and config with `kubectl kustomize`. |
| `mise run up` | Creates the `loco-demo` kind cluster and fixtures, runs the operator commands above, and checks that the dashboard serves. |
| `mise run reload` | Rebuilds the selected Core source and updates the running demo in place while keeping the workspace and fixture data. |
| `mise run deploy` | Creates the `astronomy-shop` workspace in the organization created during login, deploys the 16 services with one `loco deploy`, discovers their namespace from Loco's labels, and installs Kafka, Valkey, PostgreSQL and flagd there. The backing services support restricted pod security. |
| `mise run verify` | Runs the checks below. |
| `mise run test` | Runs the runner's regression tests. |
| `mise run down` | Deletes the cluster and fixtures this checkout created. |
| `mise run e2e` | Runs `up`, `deploy` and `verify`, then `down`. `mise run e2e -- --keep` keeps the installation. |
| `mise run report` | Files failed checks as issues in `team-loco/loco`. |

The CLIs run on the host with `HOME` set to `.state/home` and `LOCO_CREDENTIAL_STORE=file`, so the session `locoadm login` saves lives in `.state/home/.loco` and never touches your own `~/.loco` or keychain. To use it yourself:

```sh
export HOME=$PWD/.state/home LOCO_CREDENTIAL_STORE=file
.cache/bin/*/loco whoami
```

Open `http://console.loco-demo.localhost` and sign in as `demo@example.test` with password `demo-password` to see the shop in the dashboard.

Open the storefront at [shop.loco-demo-apps.localhost:8080](http://shop.loco-demo-apps.localhost:8080/) after deployment. The port binds to loopback. Kind sets the port mapping when it creates the cluster, so a cluster created before this change needs to be recreated to serve the storefront.

The API's traces go to an [Aspire dashboard](http://127.0.0.1:18888/traces/resource/loco-api) at `127.0.0.1:18888`. The API exports them to an OpenTelemetry Collector in `loco-system` (`gitops/clusters/local/config/otel-collector.yaml`), which forwards them to the `loco-demo-aspire` container on the kind network. A request's trace lists the agent work it started, such as placement delivery, builds and rollout reports, under its server span's backlinks.

Run `mise run forward-https` in a separate terminal to use the demo app HTTPS URLs on port 443. The task uses `sudo` to bind the port and forwards requests to the worker Gateway until you stop it.

The runner creates its own `loco-demo` kind cluster and uses its own kubeconfig. If kind startup or teardown is interrupted, rerun `mise run up` to clean up the partial cluster owned by this checkout and start fresh. To replace an existing installation, run `mise run down` followed by `mise run up`. A fresh cluster starts with new credentials and workspace state.

## What the test checks

| Area | Check |
| --- | --- |
| Installation | Flux reconciles the control plane and worker; `locoadm` signs in the configured admin, delivers the join token, and reports enrollment and a heartbeat with no unclaimed admins. |
| Deployments | All 16 services deploy and every resource reports healthy. |
| Storefront | The local Gateway serves the shop page and product catalog. |
| Application behavior | The runner browses the shop, adds to the cart and checks out. |
| Logs | `QueryLogs` returns logs scoped to the frontend resource. |
| Metrics | `QueryMetrics` reports the payment transaction counter increasing after checkout. |
| Traces | `GetTrace` returns a connected checkout trace across frontend, checkout, product-catalog, payment and shipping. |
| Access control | A token scoped to the demo workspace cannot query another workspace's logs, metrics or traces. |

Telemetry checks use `loco.observability.v1.ObservabilityService` with a workspace-scoped token from `TokenService`. The demo does not run `locoadm verify`: it needs the application domain's self-signed certificate trusted by `locoadm`, and on macOS that means adding it to the keychain. The deployment checks cover the same deploy and log paths.

Evidence and per-step logs go to `artifacts/`; credentials and identifiers stay in the ignored `.state/` directory.

## Application services

[`loco.yaml`](loco.yaml) declares the 16 services in one partial, `astronomy-shop`, and the deploy step applies it in one plan:

```sh
loco deploy --file loco.yaml --env production --yes --confirm-import
```

Every service except product-catalog runs the upstream release image `ghcr.io/open-telemetry/demo:3.1.0-<service>`, pinned by digest in `loco.yaml`. The 16 services are accounting, ad, cart, checkout, currency, email, fraud-detection, frontend, frontend-proxy, image-provider, load-generator, payment, product-catalog, quote, recommendation and shipping.

Services reach each other by name, as in `cart:7070`: Loco gives every service a private address under its own name in the workspace. Services whose images default to root or to a named user declare numeric `runAsUser` and `runAsGroup` values in their `loco.yaml`.

product-catalog runs `ghcr.io/team-loco/demo/product-catalog`: the upstream image with upstream's `otel-config.yml` at `/otel-config.yml`, built from [`images/product-catalog`](images/product-catalog/) by the [images workflow](.github/workflows/images.yml) and pinned by digest in `loco.yaml`.

See [`UPSTREAM.md`](UPSTREAM.md) for provenance and update instructions.

## Run unreleased Loco

`mise run setup -- --loco <source>` selects the Loco that later tasks install and use. Setup retains the last selected source; a fresh checkout defaults to `release`. Use `mise run setup -- --loco release` to switch back to the pinned release.

| Source | CLIs | Platform |
| --- | --- | --- |
| `release` | The release binaries `versions.json` pins. | The release's platform bundle. |
| `main` | Built from `origin/main` in `.cache/loco`. | Built from that checkout by `release:local` during `up` and pushed to the registry fixture. |
| A core checkout's path | Built from the checkout. | Built from the checkout by its `release:local` task during `up`, uncommitted changes included, and pushed to the registry fixture. |

```sh
mise run setup -- --loco main
mise run e2e

mise run setup -- --loco ../loco
mise run e2e
```

For both, `setup` builds the CLIs with Go. For `main`, it also trusts the cloned repository's `mise.toml` and installs its pinned tools. A supplied checkout needs its own `mise` tools installed. During `up`, `release:local` builds six images and the bundle, and writes its manifest to `.state/release.json`. Flux reads the bundle from `registry.loco-demo.localhost:5000`; each node's containerd routes that name to the fixture, which listens on `127.0.0.1:15000` for host pushes. The runner replaces the bundle digest only in `.state/gitops/`. `report` names the commit for `main` and files nothing for a checkout.

After editing or updating the selected Core checkout, run `mise run reload` from `demo`. It rebuilds the CLIs and platform bundle, then waits for Flux to reconcile the control plane and worker. With `main` selected, it fetches the latest `origin/main` first. Refresh the dashboard after the command completes.

Core applies new database migrations at startup. If your checkout changes a previously installed migration, reload stops before building the platform. Run `mise run down && mise run up && mise run deploy` to recreate the demo with the current schema. This clears the demo database and workspace.

## Versions

[`versions.json`](versions.json) pins one Loco release, which names both the CLI binaries and the platform bundle Flux installs, plus Astronomy Shop 3.1.0, its chart 0.42.3 and the kind node image. `mise.toml`, `mise.lock` and `uv.lock` pin the tools and Python dependencies. Renovate opens a pull request when Loco publishes a release; the E2E run on that pull request is the compatibility check.

## Report a failure

```sh
mise run report
```

The runner files each failed check in [`team-loco/loco`](https://github.com/team-loco/loco/issues) with the Loco version and reproduction steps, and reuses an open issue with the same title. CI on `main` and manual runs reports automatically with `LOCO_ISSUES_TOKEN`, which needs Issues write access to `team-loco/loco`.
